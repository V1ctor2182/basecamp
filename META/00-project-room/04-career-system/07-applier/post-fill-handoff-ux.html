UI 组件 4 — 自动恢复按钮(让用户少切 Chromium)

核心想法:对已知 fail 类型,卡片不应该只给 Copy / Focus / Retry 让用户自己折腾。 应该提供"我替你修"按钮 — 系统调用自己的能力(03-cv-engine 重渲染 / strategy ladder 试备用格式 / adapter 切换)直接在我们窗口里把问题搞定。

每按一次自动恢复,就少一次用户切 Chromium 的理由 → 留在我们窗口比例↑ → observer 工作时间长 → 飞轮数据收集越完整。

UI 组件 5 — Active observation(隐形,但关键)

关键创新:用户在 Chromium 里手动填的字段,系统应该自动认出来更新状态,不要求用户回 dashboard 点"我填好了"。
机制
  • 02-playwright-runtime 在 page 上挂 MutationObserver,监听 input / change 事件
  • debounce 200ms → 取该字段当前 value → 跟 expected 比较
  • 匹配 → 卡片翻绿 + flywheel 记 final_state: "filled_by_user_manual"
  • 不匹配但非空 → 卡片黄,记"用户填了但跟 expected 不同"(可能 expected 错,qa-bank 陈旧)
  • 只监听 form 区域,不监听整个 document(避免 React re-render 风暴)

UI 组件 6 — 卡片 vs Observer 是两层(数据完整性保障)

关键概念:卡片 UI 和 MutationObserver 不是同一件事。
卡片是"看得见的引导",observer 是"看不见的安全网"。卡片只能覆盖 classifier 认出来的字段;observer 把卡片管不到的兜住。两层一起才能保证 envelope 数据完整。

两层各自负责什么

维度 卡片 UI MutationObserver
角色 已知 fail 的操作建议(Copy / Focus / Retry / 自动恢复) 观察用户在 Chromium 的任何动作
覆盖 只覆盖 classifier 认识的字段(有 label + expected) 全 form 区域,包括 unknown / upload / CAPTCHA / 自定义 widget
Unknown 字段 ✗ 没卡片(我们不知道存在) ✓ 抓 user_answer + surrounding_html → 喂 classifier
File upload 只能 Focus 高亮(无法在卡片里上传) ✓ 抓 <input type=file> 的 change 事件 → file.size + file.name
CAPTCHA 只能 Focus(无法自动解) ✓ 抓 token field 出现 → captcha_solved_by_user
失败前提 用户不点卡片就没用 用户切到自己 Chrome / Safari 就废

3 层防御(越往后越被动)

Layer 1 · 卡片 UI · 主动

覆盖:classifier 认识的 fail(known label + expected)

操作:Copy / Focus / Retry / 自动恢复(re-render PDF / 试备用 phone 格式 / 切 adapter)

缺口:unknown / file picker / CAPTCHA / 复杂 widget(走 Layer 2)

↓
Layer 2 · MutationObserver · 隐形,永远在跑

覆盖:卡片管不到的 — 全部 Chromium 内 DOM 事件

抓:unknown user_answer / file.size / token appear / 任何 input 事件 → 全部进 envelope

前提:用户在我们的 Chromium 窗口里(任何方式操作都行,不限于卡片)

↓
Layer 3 · Lossy fallback · 用户切自己 Chrome / Safari 了

envelope:outcome="abandoned_to_manual"

飞轮:只用前 4 条信号(A strategy demote · D unlabeled fingerprint · G unknown ATS host · B 部分)

补救:用户回 dashboard 点 Mark applied 时弹 30 秒 opt-in 问卷(Phone 最终用什么格式 · Resume 多大 · 哪题最难)

真的只能 Chromium 操作的(observer 是唯一信号)

类型 系统能做的 系统不能做的
CAPTCHA 弹"在 Chromium 解" + observer 等 token field 出现 自动解
签名 pad Focus 跳过去 + observer 等 canvas 变化 自动签
完全没 context 的 unknown observer 抓 user_answer + surrounding_html → 喂 classifier 提前给提示(我们不知道是什么)
复杂日期 / 多选自定义 widget Focus + observer 等值变化 自动填(目前)
底线:只要用户**留在我们 Chromium 窗口**,即使我们完全没卡片 / 没 strategy / 没 adapter — observer 还能记下用户做了什么,**飞轮一样有学习材料**。 Layer 1 + 2 同时工作能覆盖 95% 场景;Layer 3 是切走自己浏览器的 fallback。

UI 组件 8 — Submit 自动检测

用户切到 Chromium 点 Submit 后,02-playwright-runtime 后台监听 — 不靠用户记得来点 Mark applied:

检测信号(三选一即触发自动 Mark)
  •   URL 变化(含 success / thank-you / confirmation)— 强信号
  •   HTTP request to /applications 返 200 + redirect — 强信号
  •   页面出现 "Thank you for applying" 类文案(adapter rule 提供 selector)— 强信号
  •   60s 无变化 — 询问用户
  •   用户关 tab / 切 URL 离开 — 询问"是否已提交?"

检测到强信号 → 自动 POST /api/career/apply/:jobId/submitted → 状态机 applied → session 关闭 + 写 history.jsonl。 Mark applied 按钮变成 fallback,仅当系统检测失败时显眼。

两个阶段 — 在线收数据 / 离线变更强

关键分清两件事:
① 在线(投递的那 2 分钟):系统**只做一件事 — 把每个动作的"事实"写进 envelope。不学,不改 rule,只记。
② 离线(投完之后,后台跑):飞轮读最近 7 天的所有 envelope,**自动 propose 改动**(strategy 重排 / 新 adapter rule / qa-bank cache), 用户 review 后人工 promote。promote 完,**下一次同 ATS 投递就更快了**。
